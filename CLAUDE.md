# Project: Dune Vamperium

## What This Is
A digital worker-placement / deck-building board game built in Godot 4 using GDScript.
Mechanically derived from **Dune: Imperium — Uprising** (with spies as a core mechanic, not a
bolt-on expansion), but the **theme is gothic horror** — vampires as the central faction/identity,
alongside other classic gothic monsters. This is **not** a Dune reskin in flavor at all; only the
underlying worker-placement/deck-building mechanics are adapted, with original factions, resources,
and cards. This file gives Claude persistent context across sessions. Update it as the project evolves.

## Design Reference: Dune Imperium / Uprising

This project's rulebooks live in `DuneManuals/` (base game, Rise of Ix, Immortality, Uprising,
Bloodlines). **Uprising is the baseline reference** for the round structure and core systems;
older-game-only mechanics (Mentat) are not used. The Dune Imperium family is a mechanical
reference only — none of its theme, names, or IP carry over.

### Core loop (adapted)
1. **Round Start** — reveal a Conflict-equivalent card; first player begins.
2. **Player Turns** — each player has **2 Actions per round** (baseline — whether this can be
   increased mid-game is an open question). Each Action is spent as one of:
   - **Place** — select **at least one Minion and at least one Plan** (multiples of either are
     optional) and send them as a set to an open board Space. The **union of pips** across every
     selected card must satisfy the Space's requirement clause. Gain Space + card effects.
   - **Hold** — reserve the Action to activate one Minion's Reveal power later, during the Reveal
     phase. The chosen Minion must still be in hand (not placed on a Space) when activated.
   - **Recall** — return any number (0 to all) of your Minions currently on the board back to your
     ready Minion hand. (Recalling 0 is legal but pointless.)
   A player who has spent/held all Actions must Reveal on their next turn; a player may also choose
   to Reveal early with unused Actions remaining (those are simply forfeited, unless held).
3. **Reveal** — every Plan still in hand automatically triggers its Reveal power for free; each
   *held* Action additionally activates the Reveal power of one chosen Minion still in hand; gain
   Reveal effects; spend pooled Money/Blood/Secret/Rapport to acquire new cards; set Combat strength.
4. **Combat** — players may play Combat Intrigue-equivalent cards, then rewards go out by strength
   (1st/2nd/3rd place).
5. **Makers** — bonus resource accumulates on unattended resource Spaces.
6. **Round End** — players draw Plans back up to hand size (Minions are **not** redrawn — see
   below), first-player marker passes, next round begins (or Endgame triggers at target Victory
   Points or when the Conflict deck empties).

### Adapted vs. base game — current mapping
| Dune Imperium / Uprising concept | This project's equivalent |
|---|---|
| Single card sent an Agent | **Minion/Plan set** sent per Action: ≥1 Minion + ≥1 Plan, multiples of either optional, union of all selected cards' pips must satisfy the Space |
| Agent meeples (fixed count, recalled automatically each round) | **Minions are a standing roster** — acquired once, never reshuffled/discarded by normal play, stay placed on a Space indefinitely until the player spends an Action on **Recall** |
| 2 (later 3) Agents per round | **2 Actions per round** baseline; each Action is Place / Hold / Recall (expandability TBD — open question) |
| Reveal turn reveals all remaining hand for free | **Plans** auto-reveal for free; **Minions** require spending 1 held Action each to activate their Reveal power |
| 8 pips: 3 action icons + 4 Faction icons + 1 Spy eye | **Action** pips (verbs: Negotiate, Fight, Hunt) · **Origin** pips (Vampire, Supernatural, Human) · **Aspect** pips (adjectives: Hideous, Insane, Arcane) · **Faction** pips (a large, swappable pool — see below) |
| Solari / Spice / Water / Persuasion | Money / Blood / Secret / Rapport (see `GameEnums.CostType`) |
| Four fixed Factions (Emperor, Spacing Guild, Bene Gesserit, Fremen) | **Many possible Factions** — Primori/Volupta/Vorace (the existing `GameEnums.RequirementType` Clans) are three of these Factions, not a separate system; which Factions are in play in a given game is determined by which Spaces are included on the board (a game could feature 0, 3, 7, or more Factions) |
| Board Space Agent-icon requirement | Space `requirement_clauses`: OR of AND-clauses over Origin + Action + Aspect (+ future Faction) pips, satisfied by the **union** of pips across an entire selected Minion/Plan set |
| Spies / observation posts / Infiltrate / Gather Intelligence | **Core mechanic from day one** (not deferred like an expansion) — design TBD |
| Sandworms, Shield Wall | Not yet planned — future consideration |
| CHOAM contracts module | Not yet planned — future consideration |
| Dreadnoughts, Tech tiles (Rise of Ix) | Not yet planned — future consideration |
| Sardaukar Commanders, Tech Module (Bloodlines) | Not yet planned — future consideration |

When implementing a system, check the matching rulebook in `DuneManuals/` for the exact mechanical
detail, then adapt names/resources/factions per the mapping above rather than copying Dune terminology.

## Card System

### Card Data (`CardData` Resource, `data/card_data/card_data.gd`)
- Two `CardType`s: **PLAN** and **MINION**.
- **Origin** pips (Minion-side identity): Vampire, Supernatural, Human — a Minion must have at least
  one. Minions always carry at least one Origin pip; Plans typically don't.
- **Action** pips (verbs): Negotiate, Fight, Hunt. Plans tend to carry Action pips.
- **Aspect** pips (adjectives): Hideous, Insane, Arcane.
- **Faction** pips: not yet implemented in `CardData` — planned new pip category. Minions tend to
  carry Faction pips. There will eventually be many possible Factions, and **Primori/Volupta/Vorace
  (the existing Clans in `GameEnums.RequirementType`) are three of them** — Clans are not a separate
  system from Factions. Only a subset of all Factions is in play in any given game, determined by
  which Spaces are on the board.
- Five possible lifecycle actions per card, each independently configurable with cost / requirement / effects:
  **Acquire, Agent, Reveal, Discard, Trash** — mirrors Dune Imperium's Agent-box/Reveal-box split, extended
  with Discard and Trash actions (cf. Uprising's Discard icon and Immortality's Unload concept).
- Each action has: `*_cost` (`GameEnums.CostType`) + `*_cost_amount`, `*_requirement` (`GameEnums.RequirementType`)
  + `*_requirement_amount`, `*_auto_execute: bool` (default `true`), and an `Array[Effect]` of effects. An action
  is only "active" if its effects array is non-empty; the Resource has a built-in validator (`status_check`)
  that flags inconsistent cost/requirement/auto_execute configuration directly in the Inspector. See
  [[auto-execute-effect-resolution]] for what `*_auto_execute` and `*_effective_auto_execute` mean.
- `card_name` is derived from the resource's filename, not a separate field.
- Pip-naming convention: Action pips are verbs (Negotiate, Fight, Hunt), Aspect pips are adjectives
  (Hideous, Insane, Arcane) — keep new pips consistent with this pattern.

### Space Data (`SpaceData` Resource, `data/space_data/space_data.gd`)
- A Space has zero or more `SpaceRequirement` clauses (OR'd together; each clause ANDs together up to one
  Origin + one Action + one Aspect pip, plus its own `cost_type`/`cost_amount` and `requirement_type`/
  `requirement_amount`). An empty clause list = open space, any selected set qualifies, no entry toll.
- Each clause's `cost_type`/`cost_amount` (spent) and `requirement_type`/`requirement_amount` (held, not spent —
  resolved via `GameState.meets_requirement()`, including Clan Rapport for PRIMORI/VOLUPTA/VORACE) are the
  mandatory toll to **send** a Minion/Plan set to the Space through that clause — enforced by
  `GameState.matched_clause()`/`total_agent_cost()` and mirrored in `Availability._clause_satisfied()` for live
  Space-selectability.
- `SpaceData.agent_cost`/`agent_cost_amount` is a separate, **optional** payment decided in the same Place
  action, resolved via the same [[auto-execute-effect-resolution]] pending-action flow as card-level Agent
  costs: if unset (or `agent_effective_auto_execute` is true), `agent_effects` fire automatically; if costed,
  it's queued for the player to trigger — or skip — from the `PendingActionPrompt` list shown right after
  the send. ~~a `RewardPrompt` Yes/No confirmation~~ → superseded, see [[auto-execute-effect-resolution]].
- `is_satisfied_by(minions: Array, plans: Array)` (on both `SpaceData` and `SpaceRequirement`) stays pip-only
  and player-agnostic — a parallel, currently-unused "pure data layer" API that mirrors `Availability`'s pip
  logic but doesn't include the resource requirement/cost checks (those are inherently player-state-dependent
  and live in `GameState`, matching where `agent_cost` enforcement already lives).

### Agent-Effect Resolution / auto_execute (`data/pending_action.gd`, `globals/game_state.gd`, `globals/pending_action_prompt.gd`)
- **Effects can resolve in any order the player chooses** — a costed Agent effect's cost may be payable using
  a resource another effect in the *same* Place grants (e.g. a Minion's free "Gain 1 Money" funding a Plan's
  "Pay 1 Blood → Gain 1 Secret" two effects later). This means costed actions can never be pre-paid as a single
  upfront bundle; each one is resolved independently, checked against the player's resources *at the moment
  they choose to trigger it*.
- Every lifecycle action (`Acquire`/`Agent`/`Reveal`/`Discard`/`Trash`, on both `CardData` and `SpaceData`'s
  single `Agent` action) has a `*_auto_execute: bool` export (default `true`) plus a computed
  `*_effective_auto_execute` getter that ANDs it with "no cost is set" — **a cost always forces the effective
  value to false at runtime**, regardless of what the Inspector checkbox says.
  `auto_execute = false` with no cost is for effects that need player input even though they're free (e.g. a
  hypothetical "Trash 1 Plan" — the player must pick which card).
- The `*_cost`/`*_cost_amount` setters actively enforce this too, not just the effective-getter: the moment
  `*_cost` becomes non-`NONE`, they force `*_auto_execute = false` directly in the Resource's stored data — so
  the Inspector checkbox visually flips off immediately instead of silently staying checked until someone
  notices the `status_check` warning. This only fires forward (cost added → force unchecked); removing a cost
  does **not** auto-re-check `auto_execute`, since a designer may have set it false for an unrelated
  needs-player-input reason. The `status_check` warning for "has a cost but auto_execute is still checked"
  remains as a belt-and-suspenders check for edge cases (e.g. a `.tres` saved before this existed, where an
  explicit serialized `auto_execute = true` line deserializes *after* `*_cost` and overwrites the auto-fix).
- **Resolution happens in two passes**, currently wired only into Place's Agent-effect trigger (the only
  spot today where multiple cards' effects fire together as one batch — Acquire/Discard/Trash have no trigger
  call sites yet, and Reveal's existing all-free-in-hand-order flow doesn't need it since no reveal_effect is
  costed today):
  1. `GameState.build_agent_pending_actions(minion_datas, plan_datas, space_data)` collects one `PendingAction`
     per selected Minion/Plan/Space that has non-empty `agent_effects`. `resolve_auto_actions(items)` fires
     every item whose `effective_auto_execute` is true immediately (the guaranteed, no-cost grants), and
     returns the rest.
  2. `board.gd._do_place()` hands whatever's left to `PendingActionPrompt.show_pending(pending)` — a modal
     list (visually in the `CardArrayPopup` family) showing each pending item's source, cost, and effect icons
     (via `ActionDisplay.populate_into`) with a Trigger button, disabled live if unaffordable.
     `GameState.try_trigger_pending(item)` spends the cost (if any) and fires the effects only if currently
     affordable, re-checked after every trigger so an earlier choice can unlock a later one. A Done button
     closes the list; anything left untriggered is simply forfeited (no partial-credit banking).
- `GameState.total_agent_cost()` narrowed to **only** the matched `SpaceRequirement` clause's cost — the
  mandatory entry toll to send the selection at all. Card-level and Space-level `agent_cost` are **no longer**
  bundled into this upfront total or auto-spent by `execute_place()`; they're resolved exclusively through the
  pending-action flow above. `can_afford_place()`/the Send-button gate follow suit — a selection can be sent
  even if the player can't currently afford one of its cards' optional Agent rewards.
- `RewardPrompt` (single Space-only Yes/No popup, built earlier the same session) is retired — fully
  superseded by the generic multi-item `PendingActionPrompt`, since a Space's optional `agent_cost` is just
  one more `PendingAction` in the same list now.

### Availability (`globals/availability.gd`)
- Implements the selection rule: a Space is available only when at least one Minion AND at least one
  Plan are selected, and the **union of pips across all selected Minions and Plans** satisfies at
  least one of the Space's requirement clauses — where "satisfies" also requires the current player to
  meet that clause's `requirement_type`/`amount` and be able to afford its `cost_type`/`amount`
  (`GameState.meets_requirement()`/`can_afford()`), not just match pips.

### Effects (`data/effects/`)
- `Effect` base class with concrete subclasses. Cards, Spaces, and FactionMilestones all reference `Array[Effect]`
  rather than encoding behavior inline — keeps data declarative and lets new effects be added without touching data classes.
- Current concrete effects: `draw_card.gd`, `gain_resource.gd` (Money/Blood/Secret), `gain_vp.gd` (+VP),
  `advance_faction_track.gd` (advance a named faction track by `amount` steps; calls `GameState.advance_faction_track()`).

### Faction Tracks (`data/faction_tracks/`)
- `FactionMilestone` Resource: `position: int` + `effects: Array[Effect]`. Fires its effects for any player who
  reaches or crosses that position while advancing. Encodes **fixed**, unconditional rewards only (e.g. +1 VP for
  everyone who hits position 2). The contested leader VP is **not** a milestone effect — it is handled by
  `FactionTrackData.leader_vp_position` and `GameState._check_faction_leader()`.
- `FactionTrackData` Resource: `faction_name: String` (must match `PlayerState.rapport` key), `max_position: int`,
  `leader_vp_position: int` (minimum position to compete for the contested VP; 0 = no leader VP on this track),
  `milestones: Array[FactionMilestone]`.
- `.tres` instances in `data/faction_tracks/`: `primori_track.tres`, `volupta_track.tres`, `vorace_track.tres`.
  All three currently have `max_position = 4`, `leader_vp_position = 4`, and one milestone at position 2 (GainVP 1).
  The position-4 faction-specific reward (spy placement, etc.) is left empty — TBD once reward Effect classes exist.
- `GameState` registrations: `faction_tracks: Dictionary` (String → FactionTrackData), `_faction_leaders: Dictionary`
  (String → int player_index, -1 = no leader yet). Tracks preloaded and registered in `GameState._ready()`.
- `GameState.advance_faction_track(player, faction_name, amount)` — increments `player.rapport[faction_name]`,
  fires crossed milestones in order, then calls `_check_faction_leader()` if new position ≥ `leader_vp_position`.
- `GameState._check_faction_leader(faction_name, player)` — if `player`'s new position **strictly exceeds** the
  current leader's, steals the contested VP (old leader −1 VP, new leader +1 VP). Ties go to first-to-reach.
- `PlayerState.rapport` (already existed as `Dict[String → int]`) doubles as the faction track position store —
  no separate field needed; the rapport threshold checks in `meets_requirement()` read from the same dict.

### Card Visuals / Scenes (`game_pieces/`)
- `card.tscn` / `card.gd` — base card visual; `minion.tscn`, `plan.tscn`, `space.tscn` — type-specific scenes,
  each with a `_zoom` variant (`minion_zoom.tscn`, `plan_zoom.tscn`, `space_zoom.tscn`) for an enlarged inspect view.
- `board.tscn` — the game board container.
- `card_scroller.gd` — hand/row scrolling UI.
- `action_display.gd` — static utility class; `populate(panel, effects, cost, cost_amount, req, req_amount)` finds the `IconMargin/IconContainer` path inside a Panel and fills it with icons; `populate_into(hbox, effects, cost, cost_amount, req, req_amount)` accepts an HBoxContainer directly (used by Space/SpaceZoom). Icon order: requirement type icon (with amount tag) → requirement.png → cost type icon (with amount tag) → cost.png → effect icons. Cost/requirement type icons and effect icons are all instantiated as `Icon` scenes carrying an amount tag; only the separator glyphs (`requirement.png`/`cost.png`) remain bare TextureRects.
- `icon.tscn` / `icon.gd` — reusable 128×128 icon scene (extends TextureRect). Supports up to two corner tags (TagLeft, TagRight) that overlay at full size using the same UV space as the base texture. All tag images are 128×128 with transparency masking them to the appropriate corner. Tags are set via the `tags: String` export (1–2 chars from `1–9`, `+`, `-`; 1 char = right tag only; 2 chars = left + right). A canvas item shader (`assets/shaders/icon_cutout.gdshader`) punches clean circular holes in the base texture wherever an active tag's back-circle image is opaque, preventing base-texture pixels from obscuring the transparent digit cutouts. `bg_opposite()` crawls up to the nearest parent Panel and returns black or white based on the panel's background luminance, for auto-coloring icons on light or dark backgrounds. `Effect.get_tags() -> String` virtual (overridden in `GainResource`) provides the tag string; `Effect.get_icon()` provides the texture.

### UI Layout
- Hand area has four panels in `HandHBoxContainer`: MinionPanel, SelectedMinionPanel, SelectedPlanPanel, PlanPanel.
- MinionPanel / PlanPanel: `SIZE_EXPAND_FILL`, no horizontal minimum — fill all space the selected panels don't claim.
- SelectedMinionPanel / SelectedPlanPanel: `SIZE_SHRINK_BEGIN` (no expand/fill), `custom_minimum_size.x` set dynamically by `Board._set_selected_panel()`: hidden + 0px when empty; 183px for 1 card; 262px for 2+ cards.

## Conventions & Patterns
*(Add coding conventions here so Claude stays consistent across sessions)*

- Use `snake_case` for variables and functions (GDScript standard)
- Card/Space Resources use `@tool` + a computed `status_check` property to surface data-validation
  warnings directly in the Inspector — follow this pattern for new Resource types where misconfiguration
  is easy (e.g. cost set but no effects).
- Cost/requirement/effect triples are repeated per lifecycle action (Acquire/Agent/Reveal/Discard/Trash)
  rather than using a generic nested struct — keep this flat pattern for consistency unless we decide to
  refactor it.
- Card and Space behavior is expressed via `Array[Effect]`, not inline logic — add new behaviors as new
  `Effect` subclasses in `data/effects/`.
- Pip naming: Action pips are verbs (Negotiate, Fight, Hunt); Aspect pips are adjectives (Hideous,
  Insane, Arcane); Origin pips are nouns (Vampire, Supernatural, Human). Keep new pips consistent
  with whichever part-of-speech pattern matches their category.
- **Card instantiation order**: always `add_child(node)` first, then `node.card_data = data`. Setting
  `card_data` before `add_child()` means `@onready` vars are null and `_load_card_image()` silently
  no-ops. This applies to every place that instantiates Minion/Plan scenes (CardArrayPopup, future pick lists).
- **`@export` setters that touch `@onready` children**: guard with `if not is_node_ready(): return`, store to a backing var, and reapply in `_ready()`. Scene loading calls export setters before `@onready` nodes exist.
- **`PackedScene` ShaderMaterial sharing**: `instantiate()` shares sub-resource ShaderMaterials across instances. Any scene that uses per-instance shader uniforms must call `material = material.duplicate()` in `_ready()` before setting uniforms.
- **`clip_children = 1` (`CLIP_CHILDREN_ONLY`) masks children by the panel stylebox's alpha, not just its shape.** The stylebox itself isn't drawn as a visible fill in this mode — it's used purely as a clip mask — but if its `bg_color` has alpha < 1, every child rendered inside gets its effective alpha multiplied down by that same amount, even if the children are themselves fully opaque. A translucent `bg_color` here silently dims/greys out everything inside the panel; keep alpha at 1.0 on any `clip_children`-masking stylebox (the RGB value is irrelevant in this mode since the fill is never actually painted).
- **A canvas_item shader that re-samples `texture(TEXTURE, UV)` and assigns the result to `COLOR` silently discards the node's `modulate`/`self_modulate` tint.** Godot pre-populates `COLOR` with `texture(TEXTURE, UV) * modulate` before your `fragment()` body runs; overwriting it with a fresh raw texture sample throws that away, so the node stops responding to modulate-based dimming/tinting entirely (while sibling non-shaded nodes, e.g. plain `TextureRect`s, keep dimming normally — a visible split that's the tell). Fix: mutate the pre-populated `COLOR` in place (e.g. `COLOR.a *= mask.a`) instead of reassigning it from a fresh `texture()` call. First hit in `icon_cutout.gdshader`, where `Space`'s dim-when-unavailable `modulate` wasn't reaching the `Icon` scene's shaded base texture (though its unshaded tag children dimmed correctly).
- **A hand-authored `.tres` file's `Array[ExtResource("id")](...)` literal (a typed array of a custom `class_name` Resource) can carry a Script-identity that doesn't match `Array[MyClass]`/`var x: MyClass` elsewhere in `.gd` code, even after adding the correct `uid=` to the `ext_resource` line and fully restarting the editor.** Symptom: `"Unable to iterate on value of type 'Array[res://path/to/script.gd]' with variable of type 'MyClass'"`, persisting across reloads. First hit with `StartingCardCount`/`default_starting_deck.tres`. Root cause not fully pinned down (adding `uid=` didn't resolve it here, unlike the general pattern); **the fix that actually worked was removing the explicit element type from the consuming side** — change `for x: MyClass in some_array:` to plain `for x in some_array:`, and `var x: MyClass = some_array[i]` to `var x = some_array[i]`, relying on duck-typing (`x.field`) instead of a static type check. The array/property can keep its `Array[MyClass]` declaration for Inspector purposes; it's specifically a *typed loop variable or typed assignment* consuming a `.tres`-literal typed array that trips this. If you hit this again, don't burn time on uid/cache fixes — just drop the type annotation on the consuming side first.

## What NOT To Do
*(Add gotchas, dead ends, or approaches already ruled out)*

- Don't model Space-sends as a strict single Minion + single Plan pair — the confirmed design is a
  **set** (≥1 Minion + ≥1 Plan, multiples allowed), matched against the union of pips.
- Don't model Minions like Dune Imperium Agent meeples that auto-return every round — Minions stay
  on their Space indefinitely until the player spends an Action on Recall.
- Don't treat Minions like deck-built cards (no automatic discard/reshuffle) — only Plans are
  deck-built; Minions are a standing roster.
- Don't copy Dune Imperium terminology directly into new content (Solari/Spice/Persuasion/Factions) —
  use this project's own resource names (Money/Blood/Secret/Rapport) and pip names (Negotiate/Fight/Hunt,
  Hideous/Insane/Arcane, Vampire/Supernatural/Human).
- Don't use "Intrigue" as a pip or mechanic name — it's reserved to avoid confusion with Dune
  Imperium's Intrigue cards; the asset/icon for this pip is now named `negotiate.png`.
- Don't treat a card's or Space's `agent_cost` as a mandatory toll spent automatically at Place time —
  that model was superseded; costed Agent actions are optional and resolved player-driven, any order,
  through the `PendingAction`/`PendingActionPrompt` flow (see [[auto-execute-effect-resolution]]), since
  their cost may be funded by another effect in the same Place. Only the matched `SpaceRequirement`
  clause's cost is still a mandatory, automatically-spent toll.
- Don't assume Agent effects fire in card-selection order or hand order — the design explicitly requires
  they be resolvable in *any* order the player picks, precisely so a later effect can be funded by an
  earlier one's reward.
